# AIGTD 语音输入交互方案

## 2. 文档目的

本文档定义 AIGTD 面向公开用户时的语音输入交互，包括：

- 输入框的点击与长按行为；
- 录音过程中的实时反馈；
- 上滑取消；
- 松手后的文字整理；
- 识别结果的编辑与发送；
- 已有草稿时的语音追加；
- 权限、网络和识别失败处理；
- 无障碍与验收要求。

本方案只定义“如何把语音转换成用户可编辑的输入”，不改变 AIGTD 对任务的理解、确认和执行安全规则。

## 3. 核心结论

AIGTD 默认采用以下语音输入模式：

> 点击输入框使用键盘；按住输入框开始说话；上滑取消；松手完成识别；识别文字进入输入框；用户可以修改或补充，最后主动点击发送。

本方案明确不采用：

- 点击一次开始录音、再点击一次停止作为默认操作；
- 按住说话、松手后自动发送；
- 停顿后自动发送；
- 录音结果未经用户确认就提交给 AIGTD；
- 以语音输入绕过现有高风险操作确认策略。

## 4. 设计目标

### 4.1 快速捕捉

用户想到一件事时，可以直接按住说话，不需要先切换语音模式，也不需要理解多个录音按钮状态。

### 4.2 可见、可控

用户在说话过程中可以看到实时识别文字，并能明确知道：

- 录音是否已经开始；
- 系统是否听到了声音；
- 当前识别到了什么；
- 松手后不会立即发送；
- 如何取消本次输入。

### 4.3 发送前可修改

语音识别结果必须先进入输入框。用户可以修正人名、时间、数字、任务标题和清单名称，再主动点击发送。

### 4.4 不增加事务管理负担

语音只是输入方式，不创建独立的语音消息类型，也不要求用户管理额外的语音会话。

### 4.5 保持执行安全

语音文本发送给 AIGTD 后，继续遵循统一执行策略：

- 普通查询直接回复；
- 明确、低风险操作按策略执行；
- 多动作展示待确认方案；
- 删除等高风险操作必须确认；
- 目标不明确时先澄清。

## 5. 输入框总体结构

## 5.1 空输入框

空输入框同时承担键盘输入入口和语音长按入口。

示意：

```text
┌──────────────────────────────────────┐
│  ◉  输入内容，或按住说话…            │
└──────────────────────────────────────┘
```

交互规则：

- 轻点输入框：打开键盘并进入文本编辑；
- 按住输入框：进入语音录入；
- 按住区域覆盖整个空输入框，不局限于一个小型麦克风按钮；
- 语音图标用于传达能力和状态，不要求用户精确按中图标。

首次展示时可以使用一次性轻提示：

> 按住输入框即可说话

不长期占用界面解释该操作。

## 5.2 已有文字

当输入框已有文字时，文本选择、光标定位和长按菜单优先，不能继续把整个输入框作为录音区域。

示意：

```text
┌────┬────────────────────────────┬────┐
│ 语音│ 明天下午提醒我联系张闯     │ 发送│
└────┴────────────────────────────┴────┘
```

交互规则：

- 点击文字区域：编辑草稿；
- 长按文字区域：遵循系统文本选择行为；
- 按住左侧语音入口：继续追加语音；
- 点击右侧发送：提交当前完整草稿；
- 语音入口和发送入口必须同时可见且语义明确。

## 6. 核心交互流程

## 6.1 轻点输入框

如果用户在长按阈值触发前松开：

- 不启动录音；
- 输入框获得焦点；
- 打开系统键盘；
- 光标进入输入区域。

建议长按触发阈值为 `150～250ms`，具体数值在真机手感测试后确定。

## 6.2 按住开始录音

达到长按阈值后：

- 启动麦克风录音；
- 触发一次轻微触觉反馈；
- 输入框进入语音状态；
- 从底部展开语音反馈层；
- 显示“正在听…”；
- 显示“松开完成”；
- 显示“上滑取消”；
- 开始展示实时识别文字和音量反馈。

示意：

```text
                 正在听…

       明天下午三点提醒我联系张闯

              · · ▮ · · ▮ · ·

                 松开完成
                 上滑取消
```

## 6.3 持续录音

录音过程中：

- 已稳定识别的文字使用正常颜色；
- 尚未稳定的尾部文字使用较浅颜色；
- 音量波形只表达麦克风正在收到声音；
- 不使用波形替代文字反馈；
- 不频繁改写已稳定的前文；
- 不显示技术性的 ASR 阶段或服务状态；
- 不使用顶部通知重复解释“开始录音”“正在识别”。

实时文字既可以显示在语音反馈层，也应同步维护在内部临时草稿中。松手之前，临时识别结果不能作为正式用户消息发送。

## 6.4 上滑取消

用户保持按住并向上滑动超过取消阈值时：

- 主提示从“松开完成”变为“松开取消”；
- 反馈颜色切换为弱红色；
- 触发一次轻微触觉反馈；
- 松手后取消本次录音；
- 恢复按住前的草稿；
- 不保留未确认的识别文字；
- 不发送任何内容；
- 不额外弹出“语音已取消”通知。

如果用户在松手前滑回有效录音区域：

- 恢复“松开完成”；
- 取消状态解除；
- 继续录音。

取消阈值需要根据设备尺寸和单手操作真机测试确定，避免轻微移动导致误取消。

## 6.5 正常松手

用户未进入取消区域并正常松手后：

1. 停止采集音频；
2. 保留当前实时文字；
3. 收起大面积录音反馈；
4. 输入框短暂显示“正在整理…”；
5. 等待最终识别结果；
6. 用最终稳定文本替换临时尾部文字；
7. 识别结果进入普通输入框；
8. 显示发送按钮；
9. 不自动发送。

示意：

```text
┌────┬────────────────────────────┬────┐
│ 语音│ 明天下午三点提醒我联系张闯 │ 发送│
└────┴────────────────────────────┴────┘
```

## 6.6 识别完成后的操作

用户可以：

- 直接点击发送；
- 点击文字并使用键盘修改；
- 按住语音入口继续补充；
- 清空草稿；
- 离开当前页面后再继续编辑。

语音识别结果在发送前只是草稿，不应进入聊天历史、Agent 上下文或任务执行链路。

## 7. 语音追加规则

## 7.1 基本原则

当输入框已有文字时，新的语音内容应插入当前光标位置；无法获得可靠光标位置时，默认追加到草稿末尾。

示例：

原草稿：

> 明天下午提醒我联系张闯

追加语音：

> 时间改成三点

结果：

> 明天下午提醒我联系张闯，时间改成三点

## 7.2 文本合并规则

- 不覆盖已有草稿；
- 不修改用户已经手动编辑的内容；
- 根据上下文补充必要空格或逗号；
- 已有自然标点时不重复添加；
- 不使用大模型在发送前重写语义；
- 只允许进行基础的空格、重复片段和明显识别尾部整理；
- 保留用户原始表达，最终语义理解交给发送后的 AIGTD。

## 8. 键盘行为

遵循“不主动制造界面跳动”的原则。

### 8.1 键盘关闭时开始语音

- 保持键盘关闭；
- 展开语音反馈层；
- 松手后不自动打开键盘；
- 用户点击识别文字时再打开键盘。

### 8.2 键盘打开时开始语音

- 可以暂时收起键盘，为反馈层和实时文字提供空间；
- 记录录音前的键盘状态；
- 松手后不强制恢复键盘；
- 用户点击文字后恢复文本编辑。

### 8.3 语音过程中切换到键盘

如果产品保留录音中的文字点击入口：

- 点击文字区域立即停止录音；
- 保留已经识别的文字；
- 打开键盘；
- 光标位于识别文字末尾；
- 不发送草稿。

第一版可以暂不提供录音中的直接键盘接管，以降低手势冲突；但松手后的文字编辑必须完整支持。

## 9. 视觉反馈

## 9.1 视觉原则

交互结构参考钉钉，但视觉表达保持 Apple 原生工具感：

- 使用系统字体；
- 使用系统语义色；
- 使用半透明 Material；
- 保留当前对话背景并适度变暗；
- 使用品牌蓝表达正常录音状态；
- 使用弱红色表达取消状态；
- 使用克制的波形和动画；
- 不使用夸张的全屏 AI 动效；
- 不展示语音服务商和技术协议名称。

## 9.2 状态文案

推荐使用：

- `正在听…`
- `松开完成`
- `上滑取消`
- `松开取消`
- `正在整理…`
- `这次没有听清，可以再试一次`
- `语音连接中断，已保留识别到的内容`

不推荐使用：

- `ASR 已连接`
- `豆包语音识别运行中`
- `正在接收 partial transcript`
- `正在合并 final transcript`
- `先去 Agent 设置语音服务`
- `再点一次语音按钮结束录音`

## 9.3 动画与触觉

- 长按触发录音时提供一次轻触觉反馈；
- 进入“松开取消”区域时提供一次不同的轻触觉反馈；
- 松手完成时可以提供一次轻量结束反馈；
- 波形只根据音量轻微变化；
- 支持 Reduce Motion，关闭非必要的展开和波形动画；
- 录音反馈层出现和收起应连贯，不影响聊天列表滚动位置。

## 10. 状态模型

建议使用以下用户可理解状态：

```text
idle
  -> pressing
  -> recording
  -> cancelling
  -> finalizing
  -> draftReady
  -> idle
```

异常分支：

```text
pressing -> permissionRequired
recording -> partialResultAvailable
recording -> recordingFailed
finalizing -> finalizationFailed
```

内部可以保留更细的技术状态，但 UI 只表达：

- 可以输入；
- 正在听；
- 松开取消；
- 正在整理；
- 文字已经进入输入框；
- 本次没有识别成功。

## 11. 权限处理

## 11.1 首次使用

长按过程中弹出系统权限窗口会打断手势，因此首次授权作为一次特殊流程处理：

1. 用户第一次按住输入框；
2. App 请求系统麦克风权限；
3. 用户允许；
4. 返回聊天界面；
5. 提示“现在可以按住说话了”；
6. 用户重新按住开始第一次正式录音。

不应在用户释放手指后自动开始后台录音。

## 11.2 权限被拒绝

在输入区域附近显示：

> 需要麦克风权限才能使用语音输入。

提供：

- `去系统设置`
- `继续打字`

不要只显示容易消失的顶部通知。

## 12. 语音服务配置

面向公开用户时，普通界面不展示具体语音服务商名称。

如果语音能力尚未准备好，使用：

> 语音输入还没有准备好。

提供：

- `设置语音输入`
- `继续打字`

具体服务商、密钥、区域和调试信息只在高级设置中展示。

不使用“先去 Agent 里配置豆包语音识别”这类内部实现文案。

## 13. 异常与恢复

## 13.1 说话时间太短

如果没有获得有效文字：

- 恢复录音前草稿；
- 显示“这次没有听清，可以再试一次”；
- 保持语音入口可用；
- 不创建空草稿。

## 13.2 最终识别失败但存在实时文字

- 保留已经获得的可靠文字；
- 将其放入输入框；
- 显示“语音连接中断，已保留识别到的内容”；
- 允许用户修改或发送；
- 不自动重试并重复追加文字。

## 13.3 完全识别失败

- 恢复录音前草稿；
- 显示简短原因；
- 提供再次按住说话和使用键盘两种路径；
- 不显示原始网络或协议错误。

## 13.4 App 进入后台或被系统中断

- 停止录音；
- 如果已有可靠文字，则保留为草稿；
- 如果没有可靠文字，则恢复录音前草稿；
- 返回 App 后明确显示当前草稿状态；
- 不自动发送。

## 13.5 页面切换

录音过程中切换 Tab 或离开聊天页时：

- 停止录音；
- 保留可靠的识别文字为草稿；
- 不继续在后台录音；
- 不发送。

## 14. 与 AIGTD 对话交互的结合

语音输入必须与文本输入使用同一条消息发送和 Agent 处理链路。

### 14.1 普通任务录入

用户按住说：

> 明天下午三点提醒我联系张闯。

松手后文字进入输入框。用户检查并点击发送，AIGTD 再按统一策略创建任务。

### 14.2 查看任务

用户按住说：

> 看看我今天还有什么事。

发送后走普通查询，不显示执行卡片。

### 14.3 调整待确认方案

当前存在待确认方案时，输入框可以显示：

> 输入或按住说出你想怎么调整

用户按住说：

> 第二条不要改，会议放到下午六点。

松手后文字进入输入框；发送后继续作用于当前唯一有效方案，不创建独立语音上下文。

### 14.4 高风险操作

语音输入不改变执行策略。即使用户通过语音说“删除这些任务”，仍必须经过目标唯一性检查和删除确认。

## 15. 无障碍

长按不能成为唯一可用的语音入口。

至少支持：

- VoiceOver 用户双击开始、再次双击结束；
- Switch Control 可触发语音开始和结束；
- 可通过辅助功能操作选择“开始语音输入”；
- 所有状态拥有清晰的 VoiceOver 标签；
- 波形不是唯一的录音状态表达；
- 状态变化可被辅助技术感知；
- 支持 Dynamic Type；
- 支持 Reduce Motion；
- 颜色之外使用文案表达正常、取消和失败状态。

建议辅助功能文案：

- 空状态：`输入消息。轻点使用键盘，辅助功能操作可开始语音输入。`
- 录音状态：`正在听。再次激活以完成。`
- 取消状态：`松开将取消本次语音输入。`
- 整理状态：`正在整理识别文字。`

## 16. 第一版范围

### 16.1 第一版必须完成

- 空输入框轻点打开键盘；
- 空输入框按住开始语音；
- 实时识别文字；
- 明确的录音反馈层；
- 上滑取消；
- 松手完成识别；
- 识别文字进入输入框；
- 用户修改后主动发送；
- 已有草稿时语音追加；
- 权限拒绝处理；
- 失败时保留可靠文字；
- 页面切换和系统中断时停止录音；
- 基本无障碍替代操作。

### 16.2 第一版暂不实现

- 松手自动发送；
- 停顿自动结束或自动发送；
- 长时间连续会议转写；
- 独立语音消息；
- 保存或播放原始录音；
- 多种语音交互模式切换；
- 根据语音来源改变 Agent 执行规则；
- 复杂全屏 AI 动效。

## 17. 验收场景

至少覆盖以下真机场景：

1. 空输入框轻点后正常打开键盘。
2. 空输入框按住后开始录音。
3. 录音开始时有明确视觉和触觉反馈。
4. 说话过程中实时文字可见。
5. 正常松手后文字进入输入框但不发送。
6. 松手后可以修改时间和人名。
7. 修改后点击发送，消息内容与输入框一致。
8. 上滑取消后恢复原草稿。
9. 进入取消区域后滑回，可以继续录音并正常完成。
10. 已有文字时可以追加一段语音。
11. 语音追加不会覆盖用户原有文字。
12. 最终识别失败但有实时文字时保留内容。
13. 完全没有识别结果时不产生空消息。
14. 首次授权流程不会错误开始后台录音。
15. 权限拒绝后提供系统设置入口。
16. 录音时切换 Tab 会停止录音且不发送。
17. 录音时 App 进入后台会停止录音且不发送。
18. 来电或音频会话中断后保留可靠草稿。
19. 待确认方案中使用语音调整仍作用于正确方案。
20. 删除类语音请求仍然要求确认。
21. VoiceOver 可以完成开始、结束、编辑和发送流程。
22. 大字体下输入框和录音反馈不截断关键操作。

## 18. 完成标准

只有同时满足以下条件，才认为语音输入交互达到公开版本要求：

- 用户无需切换语音模式即可开始说话；
- 点击和长按行为清楚且不会频繁误触；
- 录音开始和结束拥有明确反馈；
- 用户始终知道松手不会直接发送；
- 识别文字在发送前可以完整修改；
- 上滑取消可靠且不会误删除原草稿；
- 已有文字可以继续语音补充；
- 识别失败时尽可能保留用户内容；
- 语音输入不会绕过任务执行安全策略；
- 普通界面不暴露语音服务商或内部协议；
- 交互视觉符合 Apple 原生工具感；
- 无障碍用户拥有不依赖长按的替代路径。

## 19. 后续步骤

1. 基于本文档制作空闲、录音、取消、整理和草稿完成五个低保真状态。
2. 在真机上验证长按阈值、上滑距离、单手操作和键盘切换。
3. 将现有点击式语音状态映射到新的手势状态模型。
4. 拆分语音输入 UI 与 ASR 会话逻辑，避免手势、渲染和服务状态继续集中在聊天主页面。
5. 完成第一版实现后，按第 17 节进行真机验收。
6. 根据真实用户数据再决定是否需要连续语音输入或自动发送选项。
