## 2. 版本定位

`0.5.0` 已让 AIGTD 能够查询 Reminders、连续调用工具并完成多个真实操作。`0.6.0` 不继续扩张工具数量，而是把“理解、确认、执行、失败恢复、撤销”整理成用户可以自然控制的完整闭环。

本版本重点解决四个问题：

1. 用户只能点击卡片确认，无法自然地说“执行吧”或修改方案。
2. `ExecutionPolicy`、长期事务规则和结构化工具风险尚未统一决策。
3. 部分失败虽然能显示，但缺少重试失败项和撤销成功项的后续动作。
4. 新 Agent 与旧 ActionLog 撤销信息并存，无法为多动作提供可靠逆操作。

## 3. 当前基线

`v0.5.0` 已具备：

- `AgentOrchestrator`、强类型工具和真实结果回传
- 稳定 `run_id`、`call_id`、幂等账本和调用预算
- 同名任务澄清、稳定 ID 引用和写入前置条件
- 多动作、本地确认、依赖跳过和部分失败聚合
- 待确认计划持久化及 App 重启后恢复
- `ExecutionPolicy` SwiftData 模型和旧 ActionLog `undoToken`
- 删除、新建清单和多动作的按钮确认

当前缺口：

- 文本确认不会确定性地执行当前待确认计划
- 用户不能在对话里排除、替换或调整某一步后再确认
- 卡片缺少取消、重试失败项、撤销成功项等统一动作
- 新编排器没有持久化逆操作记录
- 策略设置、长期事务规则和工具风险存在重复判断
- 错误恢复仍倾向要求用户重新完整表达目标

## 4. 产品目标

### 4.1 自然控制

- 用户可以用文字确认、取消和修改当前方案。
- 文字按钮与卡片按钮调用同一条确定性执行链路。
- AIGTD 能简洁说明需要用户决定的内容，不暴露内部协议。

### 4.2 安全执行

- 所有写操作由统一策略评估是否自动执行、澄清或确认。
- 高风险、批量和目标不唯一的操作不能因模型自信而绕过本地策略。
- 长期事务规则只能收紧安全要求，不能静默放宽系统底线。

### 4.3 可恢复

- 部分失败后只重试失败项，不重复执行成功项。
- 支持撤销创建、改期、改标题、移动和完成状态。
- 撤销前重新检查任务状态，外部变化时停止并说明冲突。

### 4.4 可理解

- 卡片表达用户目标、操作对象和真实结果，不展示工具名或调用日志。
- 卡片状态稳定过渡，不突然消失或被另一张结果卡替换。

## 5. 成功指标

- 文本确认对唯一有效待确认方案的执行正确率达到 100%。
- 高风险目标不唯一时误执行次数为 0。
- 部分失败重试不重复执行成功项，重复写入次数为 0。
- 在任务未被外部修改的前提下，支持范围内的撤销成功率达到 100%。
- 普通聊天和只读查询错误显示执行卡片次数为 0。
- 用户为了完成同一目标而重新完整表达的比例较 `0.5.0` 明显下降。
- 从点击或文字确认到显示执行中状态不超过 300 毫秒。

## 6. 非目标

以下内容不进入 `0.6.0`：

- 不实现 AI 主导的优先级、预计时长和工作负载规划；进入 `0.7.0`。
- 不增加日历、邮件、通讯录或第三方工具。
- 不实现后台主动执行或未经确认自动修改系统数据。
- 不承诺恢复被删除任务；删除继续使用强确认，删除撤销另行设计。
- 不实现跨设备同步 AIGTD 的本地执行记录。
- 不允许任意历史操作无限期撤销。
- 不以新增大量中文关键词规则代替模型理解。

## 7. 核心用户场景

### 7.1 文字确认

```text
用户：把会议改到下午 5 点，再提醒我 4 点带资料。
AIGTD：展示两项待确认方案。
用户：就按这个来。
```

期望：执行当前会话中最新且唯一有效的待确认方案，结果更新在原卡片中。

### 7.2 修改方案

```text
用户：把 A、B、C 安排到周三到周五。
AIGTD：展示三项方案。
用户：B 不要改，C 放到下周一。
```

期望：旧方案失效，生成新版本方案；确认前 Reminders 不发生变化。

### 7.3 取消方案

```text
用户：算了，不执行了。
```

期望：当前待确认方案标记为已取消，后续“执行吧”不能再执行它。

### 7.4 部分失败后重试

三项移动中两项成功、一项因系统暂时不可用失败。

期望：卡片保留三项真实结果；“重试失败项”只重试失败的一项，并复用原幂等关系。

### 7.5 撤销

```text
用户：把刚才的修改撤销。
```

期望：解析到最近可撤销运行，检查当前状态仍符合撤销前置条件，再按逆序恢复成功操作。

### 7.6 外部变化冲突

用户在系统 Reminders 中手动修改了刚执行任务，然后回到 AIGTD 点击撤销。

期望：停止覆盖外部修改，说明任务已发生变化，并提供查看清单入口。

## 8. 统一交互状态机

```text
deciding
  -> awaiting_clarification
  -> awaiting_confirmation
  -> executing
  -> succeeded | partial | failed
  -> retrying
  -> undo_available
  -> undoing
  -> undone | undo_partial | undo_failed
  -> cancelled | expired
```

要求：

- 一个用户目标只维护一张主卡片。
- 状态变化更新原卡片，不新增重复卡片。
- `awaiting_confirmation` 之前不得执行写操作。
- 终态不能自动回到待确认状态。
- 旧方案版本被修改后必须失效。

## 9. FR-100 统一执行策略

新增 `ExecutionPolicyEvaluator`，输入至少包含：

- 工具风险等级
- 写操作数量和影响任务数量
- 是否拥有唯一稳定 ID
- 是否来自用户明确确认
- 是否存在前置条件快照
- `ExecutionPolicy` 设置
- 已确认的长期事务规则

输出仅允许：

- `executeImmediately`
- `requireClarification`
- `requireConfirmation`
- `reject`

默认规则：

- 普通聊天和只读查询直接完成，不显示执行卡片。
- 唯一目标的简单创建和简单修改可按设置自动执行。
- 多动作、批量操作和新建清单默认确认。
- 删除始终遵循删除确认策略；目标不唯一时先澄清。
- 缺少稳定 ID 或写入快照时不得执行修改型操作。
- 长期规则可以要求更多确认，但不能关闭目标唯一性和前置条件校验。

## 10. FR-200 待确认交互

新增版本化 `PendingInteraction`：

```text
interactionID
sessionID
runID
version
goal
pendingCalls
priorResults
createdAt
expiresAt
status
```

规则：

- 每个会话最多一个 active 待确认交互。
- 新方案取代旧方案时，旧版本标记为 superseded。
- 默认 24 小时后过期；涉及任务状态变化时仍以执行前置条件为准。
- App 重启后可恢复卡片、文字确认和按钮确认。
- 文本确认必须由本地先解析到唯一 active 交互，再调用 `executeConfirmed`。
- 没有 active 交互时，“执行吧”只能澄清，不能猜测历史方案。

支持的自然表达包括：

- 确认：`执行吧`、`就按这个来`、`确认执行`
- 取消：`算了`、`不要执行`、`取消这个方案`
- 修改：`第二条不要改`、`把第三条改到周五`、`只执行前两条`

模型负责理解修改内容；本地负责解析交互身份、版本和是否可执行。

## 11. FR-300 方案修改

- 修改待确认方案时不复用旧 `call_id` 伪装成同一操作。
- 新方案必须生成新版本和新的写调用 ID。
- 读取结果仍有效时可以复用；任务已变化时必须重新查询。
- 用户排除的操作应从新方案中移除，而不是标记成功。
- 修改完成后继续保持待确认，除非用户同一句明确要求立即执行且策略允许。
- 卡片显示“已按你的要求调整”，并列出最终会执行的内容。

## 12. FR-400 失败恢复

失败分为：

- `retryable`：网络中断、超时、临时存储不可用。
- `refreshRequired`：任务不存在、前置条件冲突、清单变化。
- `userActionRequired`：权限关闭、凭证缺失、目标歧义。
- `terminal`：协议非法、未知工具、预算耗尽。

恢复规则：

- 自动参数修正最多一次，且不能改变用户目标或扩大范围。
- 自动重试写操作最多一次，必须复用原 `run_id + call_id`。
- 用户点击“重试失败项”时只选择失败或超时调用。
- 成功、无需修改和已应用调用不得重新执行。
- 前置条件冲突必须重新查询并再次确认，不能直接覆盖。
- 权限和凭证问题只提供修复入口，不循环重试。

## 13. FR-500 撤销

新增持久化 `UndoRecord`，在写入前保存生成逆操作所需的最小快照。

支持范围：

| 正向操作 | 逆操作 |
| --- | --- |
| 创建任务 | 删除本次创建且仍未被外部修改的任务 |
| 修改标题/时间/备注 | 恢复原字段 |
| 移动任务 | 移回原清单 |
| 完成/恢复任务 | 恢复原完成状态 |

规则：

- 只为真实成功的写操作生成逆操作。
- 批量撤销按正向执行的相反顺序运行。
- 撤销入口默认显示 10 分钟；过期后记录仍可诊断但不可执行。
- 撤销本身拥有独立 `run_id` 和幂等调用。
- 撤销前检查任务仍处于正向操作产生的状态。
- 外部修改、任务缺失或清单缺失时停止对应逆操作并显示真实原因。
- 删除任务不支持恢复，不生成虚假的撤销能力。

## 14. FR-600 卡片交互

待确认卡片展示：

- 用户目标
- 将要操作的任务和关键变化
- 风险提示，仅在确有必要时展示
- `执行这个计划`、`调整`、`取消`

执行结果卡片展示：

- 简短结论
- 每项成功、失败、跳过或无需修改
- 合适时展示 `重试失败项`、`撤销`、`查看清单`

交互要求：

- pending 状态紧随助手文字出现。
- pending 到结果使用原卡片内容和尺寸的平滑过渡。
- 终态卡片不自动消失。
- 普通聊天和只读查询不创建占位执行卡片。
- 不显示 `intent`、工具名、schema、call ID 或内部错误堆栈。

## 15. FR-700 对话文案

- 先给结果，再给必要补充。
- 澄清问题必须具体列出需要用户选择的差异。
- 确认文案说明“将做什么”，不重复内部计划描述。
- 部分失败明确成功数、失败数和可选下一步。
- 撤销成功使用“已恢复”，不使用容易与完成状态混淆的“已完成”。
- 任何失败文案不得声称系统状态已经改变。

## 16. 数据与兼容性

新增数据建议采用独立版本化 Codable 存储，避免在 `0.6.0` 扩大 SwiftData 迁移风险：

- `AgentPendingInteractionStore`
- `AgentUndoStore`
- `AgentRecoveryState`

兼容要求：

- `0.5.0` 聊天、设置、长期记忆和 ActionLog 可继续读取。
- 旧 `undoToken` 只用于旧卡片兼容，不升级为多动作撤销记录。
- 无法解码的新状态必须安全失效，不得恢复并执行半份计划。
- 清除会话上下文时同步清除该会话的待确认交互，不删除 Reminders。

## 17. 隐私与安全

- 撤销快照默认只保存恢复所需字段，不复制无关备注。
- 备注仅在用户允许读取备注且该操作确实修改备注时进入快照。
- 诊断默认记录状态、类别、长度和哈希，不保存完整任务文本。
- API Key、凭证和模型原始响应不得进入待确认或撤销存储。
- 所有本地恢复操作继续通过允许列表工具执行，不直接反射调用 EventKit。

## 18. 诊断与指标

每次交互记录：

- 进入确认、澄清、执行、重试、撤销的阶段时间
- 策略结论和不含原始文本的原因码
- 方案版本、操作数量和最终状态
- 重试是否复用幂等键
- 撤销可用、成功、部分失败或冲突

不得记录：

- 完整模型思考过程
- API Key 或 Authorization Header
- 默认完整标题、备注和会话正文

## 19. 测试计划

### 19.1 自动测试

在 `0.5.0` 的 222 个 XCTest 方法基础上新增不少于 60 项：

- 策略矩阵不少于 15 项
- 文本确认、取消和方案版本不少于 12 项
- 方案修改不少于 8 项
- 失败分类和只重试失败项不少于 10 项
- 撤销生成、逆序执行、冲突和过期不少于 12 项
- 卡片状态映射和持久化恢复不少于 8 项

多工具评测 fixture 从 40 条扩充到不少于 70 条，新增自然确认、方案修改、撤销和失败恢复类别。

### 19.2 真机验收

至少覆盖：

1. 单任务直接创建。
2. 多动作按钮确认。
3. 多动作文字确认。
4. 取消待确认方案。
5. 排除方案中的第二项。
6. 修改方案中的时间。
7. App 重启后文字确认。
8. 同名任务继续要求澄清。
9. 部分失败只重试失败项。
10. 创建任务后撤销。
11. 改期后撤销。
12. 移动后撤销。
13. 完成后撤销。
14. 外部修改后拒绝撤销覆盖。
15. 普通聊天不闪现卡片。

## 20. 发布门槛

- `0.5.0` 核心能力无回退。
- 自动测试和新增评测达到目标且全部通过。
- 15 组真机核心场景全部通过。
- 删除、同名目标和批量写入没有高风险误执行。
- 文本确认与按钮确认执行同一份方案，结果一致。
- 重试失败项不重复执行成功项。
- 支持范围内的撤销在无外部冲突时全部成功。
- TestFlight 覆盖升级不丢失聊天、设置、长期记忆和 Reminders 数据。

## 21. 开发阶段

### 阶段 A：交互状态与策略

- 建立 `PendingInteraction` 和统一策略评估器。
- 将现有确认判断迁移到策略层。
- 补齐策略矩阵测试。

完成标准：相同输入在按钮和文字路径得到一致的确认结论。

### 阶段 B：文字确认与方案修改

- 解析当前会话 active 交互。
- 支持确认、取消、排除和调整。
- 处理版本失效和 App 重启恢复。

完成标准：文字确认不依赖模糊历史猜测，修改前无写入。

### 阶段 C：恢复与重试

- 建立错误分类和恢复动作。
- 只重试失败项并复用幂等键。
- 完成部分失败卡片动作。

完成标准：成功项不重复执行，冲突不会被自动覆盖。

### 阶段 D：撤销

- 建立最小写前快照和逆操作生成器。
- 实现单动作与批量逆序撤销。
- 增加过期和外部变化保护。

完成标准：支持范围内的操作可验证恢复，删除不显示虚假撤销。

### 阶段 E：卡片与文案

- 统一待确认、执行、部分失败和撤销状态。
- 调整动画、按钮和自然语言文案。
- 清除用户界面的内部协议字段。

完成标准：一份计划只维护一张稳定卡片。

### 阶段 F：回归与发布

- 扩充评测和真机验收文档。
- 运行完整自动测试和 TestFlight 覆盖升级。
- 更新发布说明、Changelog 和版本标签。

完成标准：满足本 PRD 的全部发布门槛。

## 22. 风险与应对

### 风险一：文字确认执行错误历史方案

应对：只允许当前会话唯一 active 且版本未过期的交互被本地确认。

### 风险二：撤销覆盖用户在 Reminders 中的后续修改

应对：逆操作携带正向结果快照，执行前强制比较当前状态。

### 风险三：重试造成重复创建

应对：自动重试复用原 `run_id + call_id`，用户发起的新方案使用新调用 ID。

### 风险四：同时维护新旧执行链路导致分支继续膨胀

应对：新能力只进入结构化 Agent；旧链路仅保留历史卡片读取兼容。

### 风险五：范围滑入智能规划

应对：本版本只允许用户修改明确方案，不根据优先级和工时自动优化；智能规划留给 `0.7.0`。

## 23. 完成定义
